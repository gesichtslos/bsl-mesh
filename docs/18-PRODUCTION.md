# Публичный HTTPS для bslmesh.ru

Эта конфигурация подготовлена отдельно от действующего staging. Запуск `compose.production.yaml`, публикация портов 80 и 443, изменение DNS, SSH и firewall в этот документ не входят и выполняются только после отдельного разрешения.

## Почему staging HTTPS отвечает TLS alert 80

В `Caddyfile` глобальная опция `auto_https off` отключает управление сертификатами у HTTP-сервера. Блок `tls internal` при этом создаёт внутренний центр сертификации и устанавливает его в доверенное хранилище контейнера, но слушатель `:443` не получает сертификат: в адаптированной конфигурации у обоих серверов `automatic_https.disable: true`, а загруженных сертификатов нет. Клиент завершает рукопожатие с alert 80, `internal error`.

Проверка TLS у клиента здесь ни при чём. `Caddyfile` staging оставлен без изменений. Рабочий вариант — отдельный `Caddyfile.production`: обычный автоматический HTTPS для имени `bslmesh.ru`, без `auto_https off` и без `tls internal`. Caddy запрашивает и продлевает сертификат через ACME. Для уведомлений нужна переменная `CADDY_ACME_EMAIL`; адрес не хранится в Git.

Пока production Compose не запущен, порты 80 и 443 остаются закрытыми для сети, и сертификат не выпускается.

## Отдельная база production

Staging остаётся на своём томе `bsl-mesh-staging_pgdata`. Production использует другой том:

```yaml
volumes:
  pgdata:
    name: bsl-mesh-production_pgdata
    external: true
```

`external: true` не создаёт том. Перед первым запуском его создают явно:

```bash
docker volume create bsl-mesh-production_pgdata
```

Пока этого тома нет, `docker compose -f compose.production.yaml up` завершается ошибкой. Смена имени проекта не приводит к появлению другой пустой базы. Остановка staging для освобождения тома не нужна: каталоги данных разные, и staging может продолжать работать.

Docker по-прежнему позволяет двум контейнерам смонтировать один и тот же том. Поэтому production не ссылается на том staging. `scripts/check-production-volume.sh` только сообщает, занят ли уже `bsl-mesh-production_pgdata`. Compose его не вызывает и контейнеры не останавливает.

PostgreSQL и Fastify не публикуют порты хоста. Наружу в файле описаны только `80/tcp`, `443/tcp` и `443/udp` у Caddy. UDP нужен HTTP/3, который Caddy включает на публичном 443. Эти порты появятся в сети только в момент запуска файла.

### Первоначальный запуск

Первый запуск на пустом `bsl-mesh-production_pgdata` создаёт новую базу. Он не читает и не копирует данные staging.

1. Добавить на сервере, не в Git, `MIGRATE_PASSWORD` и `CADDY_ACME_EMAIL`. Пароли не отправлять в чат.
2. Создать пустой том командой выше. Не удалять тома, секреты и резервные копии staging.
3. Запустить `scripts/check-production-volume.sh`. Если свой production-том уже занят другим контейнером, второй PostgreSQL на него не ставить.
4. Запускать production Compose только после отдельного разрешения на публичные порты.

На пустом томе PostgreSQL выполняет `docker/postgres/init`. Скрипт создаёт `bslmesh_admin`, `bslmesh_app` и, когда задан `MIGRATE_PASSWORD`, `bslmesh_migrator`. Затем служба `migrate` передаёт владение объектами мигратору и применяет миграции от `bslmesh_migrator`. Постоянный процесс приложения запускает `node dist/server.js` от `bslmesh_app`.

### Перенос данных

Автоматического переноса staging нет. Если содержимое staging когда-нибудь понадобится в production, это отдельная операция: снять резервную копию и восстановить её в новую базу по `scripts/restore-backup.sh`, с уже существующим отказом восстанавливать прямо в рабочую базу без отдельного подтверждения. Запуск Compose эту копию не подставляет.

После перезагрузки хоста Docker снова поднимает `db`, `app` и `caddy` по политике `unless-stopped`. Одноразовая служба `migrate` не стартует повторно: схема уже применена, а процесс приложения не выполняет DDL.

Обновление схемы после новой версии образа:

```bash
docker compose --env-file /opt/bsl-mesh/.env -f compose.production.yaml up -d --no-deps migrate
docker compose --env-file /opt/bsl-mesh/.env -f compose.production.yaml up -d
```

Первая команда применяет права и миграции. Вторая обновляет приложение. Если миграция не прошла, приложение остаётся на прежнем контейнере до успешного завершения `migrate`.

## Полномочия

Staging по-прежнему запускает миграции из `docker/entrypoint.sh` от `bslmesh_app`. Production этого не делает.

`docker/production-migrate.sh` один раз подключается администратором, передаёт владение объектами роли `bslmesh_migrator` и только потом запускает `node dist/migrate.js` от этой роли. Скрипт повторяется после миграций и снимает у приложения право записи в `schema_migrations`. Постоянный процесс получает `node dist/server.js`, пользователя `bslmesh_app` и права `SELECT`, `INSERT`, `UPDATE`, `DELETE`. Права `CREATE` на базу и схему у приложения сняты. Новые таблицы, созданные мигратором, получают те же права на данные через default privileges.

Скрипт меняет владельца только внутри целевой базы. Он не использует `REASSIGN OWNED`, потому что эта команда переназначила бы и общие объекты кластера. Для production цель может быть только `bslmesh_dev`.

Повторный запуск уже заполненного production-тома инициализацию не повторяет. Следующие изменения схемы выполняет служба `migrate`, а не скрипт первого запуска PostgreSQL.

## Резервные копии вне VPS

Локальный дамп и проверка восстановления в отдельную базу остаются в `scripts/backup.sh` и `scripts/restore-backup.sh`. Цель `bslmesh_dev` по-прежнему отклоняется без отдельного подтверждения.

Внешняя копия — это отдельный файл в S3-совместимом хранилище. `scripts/production-backup.sh` снимает `pg_dump` в формате custom и шифрует его AES-256-GCM до отправки. Ключ выводится из `BACKUP_PASSPHRASE` через scrypt. Незашифрованный дамп в постоянное хранилище не записывается: на время шифрования он находится в памяти процесса. Временный шифртекст и, только на время восстановления, временный расшифрованный файл удаляются при любом завершении команды. В хранилище остаётся зашифрованный объект.

Команда требует Node.js 24.22.0 и Docker. Без полного набора параметров она завершается кодом 2 и ничего не отправляет:

- `BACKUP_S3_ENDPOINT`
- `BACKUP_S3_BUCKET`
- `BACKUP_S3_REGION`
- `BACKUP_S3_ACCESS_KEY_ID`
- `BACKUP_S3_SECRET_ACCESS_KEY`
- `BACKUP_PASSPHRASE` — не короче 16 символов

Секретный ключ и парольная фраза задаются в окружении процесса, не в Git и не в аргументах команды. Ошибка создания дампа, шифрования или передачи завершает команду неуспешно; объект при неуспешной передаче не считается копией. В журнале печатаются имя объекта и размер шифртекста. Пароли, ключи и содержимое дампа не печатаются.

Бакет создаётся один раз: `scripts/production-backup.sh create-bucket`. Копия:

```bash
scripts/production-backup.sh
```

Проверка целостности скачивает объект, сверяет SHA-256 шифртекста с метаданными и проверяет метку подлинности AES-GCM:

```bash
scripts/production-backup.sh verify bslmesh/bslmesh_dev-TIMESTAMPZ-SUFFIX.bsm1
```

Восстановление идёт в новую пустую базу, не в `bslmesh_dev`:

```bash
scripts/production-restore.sh bslmesh/bslmesh_dev-TIMESTAMPZ-SUFFIX.bsm1 bslmesh_backup_check
```

Если база с таким именем уже есть, команда отказывается. Если восстановление обрывается, созданная этой командой база удаляется. `scripts/production-backup.sh --self-test` проверяет только локальное шифрование и сеть не использует. `scripts/production-backup-rehearsal.sh` повторяет выгрузку, проверку и восстановление на временных PostgreSQL и S3-совместимом сервере с фиктивными ключами. Планировщик, срок хранения и мониторинг сюда не входят.

## Firewall и SSH

Сейчас ничего из этого не применяется.

Docker публикует порты через собственные правила iptables. Выключенный или включённый UFW на входящем трафике сам по себе не закрывает порт, опубликованный Compose. Внешний контур — firewall панели REG.Cloud. Перед публичным запуском в панели нужно разрешить `80/tcp`, `443/tcp` и `443/udp`, а SSH оставить только с административного адреса. На хосте фильтр для пересылаемого трафика — цепочка `DOCKER-USER`, а не только политика UFW.

Уже проверенный вход по ключу сохраняется. Отключение пароля делается только после отдельного разрешения и в таком порядке:

1. Открыть вторую сессию тем же ключом и убедиться, что она входит без пароля.
2. Сверить `sshd -T`: ожидаются `pubkeyauthentication yes` и рабочий ключ.
3. Установить `PasswordAuthentication no`, `KbdInteractiveAuthentication no` и `PermitRootLogin prohibit-password`.
4. Выполнить перечитывание конфигурации sshd, не разрывая уже открытую сессию.
5. Новым подключением проверить вход по ключу. Консоль REG.Cloud остаётся способом восстановления, если новый вход не удался.

Парольный вход не отключается, пока вторая сессия по ключу не проверена.
