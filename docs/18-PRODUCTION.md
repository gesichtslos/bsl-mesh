# Публичный HTTPS для bslmesh.ru

Эта конфигурация подготовлена отдельно от действующего staging. Запуск `compose.production.yaml`, публикация портов 80 и 443, изменение DNS, SSH и firewall в этот документ не входят и выполняются только после отдельного разрешения.

## Почему staging HTTPS отвечает TLS alert 80

В `Caddyfile` глобальная опция `auto_https off` отключает управление сертификатами у HTTP-сервера. Блок `tls internal` при этом создаёт внутренний центр сертификации и устанавливает его в доверенное хранилище контейнера, но слушатель `:443` не получает сертификат: в адаптированной конфигурации у обоих серверов `automatic_https.disable: true`, а загруженных сертификатов нет. Клиент завершает рукопожатие с alert 80, `internal error`.

Проверка TLS у клиента здесь ни при чём. `Caddyfile` staging оставлен без изменений. Рабочий вариант — отдельный `Caddyfile.production`: обычный автоматический HTTPS для имени `bslmesh.ru`, без `auto_https off` и без `tls internal`. Caddy запрашивает и продлевает сертификат через ACME. Для уведомлений нужна переменная `CADDY_ACME_EMAIL`; адрес не хранится в Git.

Пока production Compose не запущен, порты 80 и 443 остаются закрытыми для сети, и сертификат не выпускается.

## Compose и переход с staging

`compose.production.yaml` использует отдельное имя проекта `bsl-mesh-production`, но том PostgreSQL указан явно:

```yaml
volumes:
  pgdata:
    name: bsl-mesh-staging_pgdata
    external: true
```

`external: true` не создаёт новый пустой том, если существующий отсутствует: `up` завершается ошибкой. Новые тома есть только у данных Caddy; внутренний центр сертификации staging в них не переносится.

`external: true` не запрещает двум контейнерам одновременно смонтировать уже существующий том. Локальная проверка на отдельном временном томе, не на `bsl-mesh-staging_pgdata`, показала, что два контейнера `postgres:18.6` монтируют один и тот же каталог данных и оба сообщают готовность принимать соединения. Docker не ставит на том исключительную блокировку, а проверка `postmaster.pid` не видит процесс в другом контейнере. Успешный `docker compose config` этого не обнаруживает.

Перед будущим запуском нужно остановить контейнер staging и убедиться, что том никто не использует: `scripts/check-production-volume.sh`. Compose этот скрипт не вызывает. Если скрипт показывает работающий контейнер, production запускать нельзя.

PostgreSQL и Fastify не публикуют порты хоста. Наружу в файле описаны только `80/tcp`, `443/tcp` и `443/udp` у Caddy. UDP нужен HTTP/3, который Caddy включает на публичном 443. Эти порты появятся в сети только в момент запуска файла.

Безопасный переход, когда он будет разрешён:

1. Ещё раз посмотреть `docker volume ls` и убедиться, что рабочий том называется `bsl-mesh-staging_pgdata`.
2. Добавить на сервере, не в Git, `MIGRATE_PASSWORD` и `CADDY_ACME_EMAIL`. Пароли не отправлять в чат.
3. Остановить staging: `docker compose -f compose.staging.yaml stop`. Не использовать `down -v` и не удалять тома, секреты и резервные копии.
4. Запустить `scripts/check-production-volume.sh` и убедиться, что работающих контейнеров на томе нет.
5. Запустить production только после разрешения на публичные порты. Файл Compose сам второй экземпляр PostgreSQL не останавливает.

После перезагрузки хоста Docker снова поднимает `db`, `app` и `caddy` по политике `unless-stopped`. Одноразовая служба `migrate` не стартует повторно: схема уже применена, а процесс приложения не выполняет DDL.

Обновление схемы после новой версии образа:

```bash
docker compose --env-file /opt/bsl-mesh/.env -f compose.production.yaml up -d --no-deps migrate
docker compose --env-file /opt/bsl-mesh/.env -f compose.production.yaml up -d
```

Первая команда применяет права и миграции. Вторая обновляет приложение. Если миграция не прошла, приложение остаётся на прежнем контейнере до успешного завершения `migrate`.

## Полномочия

Staging по-прежнему запускает миграции из `docker/entrypoint.sh` от `bslmesh_app`. Production этого не делает.

`docker/production-migrate.sh` один раз подключается администратором, передаёт владение объектами роли `bslmesh_migrator` и только потом запускает `node dist/migrate.js` от этой роли. Скрипт повторяется после миграций и снимает у приложения право записи в `schema_migrations`. Постоянный процесс получает `node dist/server.js`, пользователя `bslmesh_app` и права `SELECT`, `INSERT`, `UPDATE`, `DELETE`. Права `CREATE` на базу и схему у приложения сняты. Новые таблицы, созданные мигратором, получают те же права на данные через default privileges.

Скрипт меняет владельца только внутри целевой базы. Он не использует `REASSIGN OWNED`, потому что эта команда переназначила бы и общие объекты кластера. Для production цель может быть только `bslmesh_dev`.

Инициализация нового тома не повторяется на уже заполненном `bsl-mesh-staging_pgdata`. Поэтому переход выполняет отдельная служба `migrate`, а не скрипт первого запуска PostgreSQL.

## Резервные копии вне VPS

Локальный дамп и проверка восстановления в отдельную базу остаются в `scripts/backup.sh` и `scripts/restore-backup.sh`. Цель `bslmesh_dev` по-прежнему отклоняется без отдельного подтверждения.

`scripts/production-backup.sh --self-test` проверяет только локальное шифрование AES-256-CBC и ничего не отправляет. Без внешнего хранилища обычный запуск завершается кодом 2 и не создаёт выгрузку. Нужны параметры, которые задаются на сервере и не присылаются в чат:

- `BACKUP_S3_ENDPOINT`
- `BACKUP_S3_BUCKET`
- `BACKUP_S3_REGION`
- `BACKUP_S3_ACCESS_KEY_ID`
- `BACKUP_S3_SECRET_ACCESS_KEY`
- `BACKUP_PASSPHRASE`

Секретный ключ и парольная фраза не должны попадать в Git. Парольную фразу после настройки нельзя оставлять единственной копией на VPS: без неё копия не расшифровывается. Платное хранилище не заказывается, пока эти параметры не предоставлены отдельно.

Проверка восстановления выполняется в новую базу, не в `bslmesh_dev`.

## Firewall и SSH

Сейчас ничего из этого не применяется.

Docker публикует порты через собственные правила iptables. Выключенный или включённый UFW на входящем трафике сам по себе не закрывает порт, опубликованный Compose. Внешний контур — firewall панели REG.Cloud. Перед публичным запуском в панели нужно разрешить `80/tcp`, `443/tcp` и `443/udp`, а SSH оставить только с административного адреса. На хосте фильтр для пересылаемого трафика — цепочка `DOCKER-USER`, а не только политика UFW.

Уже проверенный вход по ключу сохраняется. Отключение пароля делается только после отдельного разрешения и в таком порядке:

1. Открыть вторую сессию тем же ключом и убедиться, что она входит без пароля.
2. Сверить `sshd -T`: ожидаются `pubkeyauthentication yes` и рабочий ключ.
3. Установить `PasswordAuthentication no`, `KbdInteractiveAuthentication no` и `PermitRootLogin prohibit-password`.
4. Выполнить перечитывание конфигурации sshd, не разрывая уже открытую сессию.
5. Новым подключением проверить вход по ключу. Консоль REG.Cloud остаётся способом восстановления, если новый вход не удался.

Парольный вход не отключается, пока вторая сессия по ключу не проверена.
