# AGENTS.md — инструкция агентам, реализующим BSL Mesh

## Миссия

Реализовать минимально пригодную к использованию агентную платформу для независимых участников BSL (Business Script Language), где основная единица информации — контекстуализированное утверждение с доказательствами, а ключевой продукт — асинхронные технические митапы и переносимые результаты.

**Не переосмыслять продукт как обычный чат, CRUD-форум или витрину AI-аватаров.** Содержательность, проверяемость, права владельцев и пригодность MCP являются обязательными.

## Правила разработки

- Работать P0-задачами по зависимостям из Roadmap; не начинать P1/P2, пока vertical slice не работает end-to-end.
- Сначала фиксировать тестируемые контракты, затем реализовывать; обновлять документацию при изменении контрактов.
- Уведомления серверного scheduler **не означают способность запускать чужих интерактивных агентов**.
- Агенты пользователей не должны автоматически отправлять исходники, промпты или логи во внешнюю сеть.
- Репутация не строится по числу постов; `synthetic` никогда не считается реальным доказательством.
- Не использовать LLM для проверки доказательств как единственный механизм истинности; LLM может предлагать черновик или находить схожие claims, но не свидетельствовать о воспроизведении, которого не было.
- REST и MCP работают с **одними application services**. Не дублировать авторизацию в двух несовместимых реализациях.
- Все write API обязаны иметь scopes, idempotency и аудит без секретов.
- Для статуса `reproduced` проверять происхождение результата, контекст и независимость; не повышать статус по количеству реплик.
- Не утверждать, что реализована поддержка клиентского хоста, пока не выполнен реальный integration test.
- Не добавлять внешние зависимости, инфраструктуру или сложные frameworks без объяснения необходимости.
- Не публиковать решения в production без CI, миграций, backup/restore и security negative tests.

## Требования к сдаче каждой задачи

В pull request / Kanban issue дать: краткий контекст, что изменено, список тестов и реальные результаты, контракт (если затронут), ограничения, совместимость, ручные шаги проверки и возможный откат.

Если в требованиях обнаружено противоречие, не выдумывать ответ: описать противоречие, предложить минимальное решение, зафиксировать в ADR. Вопрос владельцу задавать только если невозможно безопасно продолжать с обратимым решением.

## Проверка ключевого сценария

1. Owner создаёт два различных агентных аккаунта с безопасными полномочиями.
2. Агент A публикует case и claim в тестовой BSL-среде (с отметкой synthetic).
3. Агент B обнаруживает его через MCP и добавляет контрпример с отдельным evidence.
4. Куратор создаёт асинхронную встречу и связывает оба материала.
5. После обсуждения публикуется synthesis с указанием разногласий.
6. Агент C через `search_knowledge` находит итог и видит статус/ограничения/ссылки.
7. Никакое synthetic evidence не повышает claim до reproduced или recommended.

После появления реальных участников тест повторяется с органическими, разрешёнными данными. Демонстрационный тест не доказывает реальную полезность.

## Терминология

- BSL — только Business Script Language.
- Mesh — граф обмена опытом между независимыми системами, а не требование P2P транспорта.
- Meetup — асинхронное тематическое событие с документированным итогом.
- Owner — владелец полномочий и ответственности.
- Agent — программный исполнитель, а не доказательство сознательности или автономности.
- Evidence — поддающееся проверке наблюдение, не синоним убедительного текста.

## Новый инвариант v0.2: newcomer first

- Реализовать публичный **Zero-MCP** сценарий, в котором новичок отправляет агента на сайт за коллективными рекомендациями, а агент после локального одобрения разворачивает Tools/Skills/Rules/MCP и выполняет безопасный smoke-test.
- Нормативные документы: `07-BOOTSTRAP.md`, `08-CLIENT-SECURITY-MANIFEST.md`, `09-STARTER-CONTRACTS.md`. Не заменять манифест «правилами из ответа MCP»: локальное правило передаётся владельцем из доверенного канала.
- Никакой агент-разработчик платформы не вправе реализовать «автоинсталляцию по воле сайта» или отправку данных клиента. Из site API должны приходить **декларативные** наборы с evidence/compatibility/version/provenance, не команды подмены локальной политики.
- Не считать `published`, «мейнстрим» и endorsement эквивалентом независимой проверки; предотвращать накрутку и коммерческие перекосы.
- Все демонстрационные starter profiles, bundle manifests и smoke tests иметь `source_kind=synthetic` до первых фактических независимых проверок. Не обещать, что рекомендованные интеграции уже существуют.
- Чек-лист сдачи BM-018–BM-021: полноценная проверка Zero-MCP нового агента с локальным манифестом, планом/approval, сохранением настроек, smoke-tests, rollback и инъекционными негативными сценариями.
