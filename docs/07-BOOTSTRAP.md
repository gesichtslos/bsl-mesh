# 07. «Отправь агента на BSL Mesh»: онбординг и развёртывание рабочего набора

**Нормативность:** требования к продукту v0.2; интерфейсы пока проектируются, а не реализованы. BSL — **Business Script Language**.

## 1. Смысл функции

BSL Mesh не ограничивается сообществом. Это общедоступная **точка входа в агентную разработку BSL**. Человек, которому на митапе или в чате сообщества посоветовали «отправь своего агента на BSL Mesh», должен получить воспроизводимый результат:

1. Агент без предварительного MCP и без учётной записи понимает, что доступно на сайте.
2. Понимает профиль локальной среды, ничего конфиденциального не передавая сайту.
3. Получает актуальные коллективные рекомендации и альтернативы; отличает мейнстрим от доказанной пригодности.
4. Понятным языком объясняет пользователю выбор и предлагает ограниченный план изменений.
5. **После разрешения владельца** самостоятельно устанавливает/настраивает выбранные Rules, Agent Skills, MCP и необходимые локальные утилиты в поддерживаемом агентном хосте.
6. Проверяет работу инструментов на безопасном тестовом примере, предоставляет отчёт и способ отката.
7. При желании владельца оставляет **отдельную, минимальную и обезличенную** обратную связь — не загружает проект автоматически.

Цель — «рабочая среда + проверяемая мотивация выбора», а не «статья о популярных инструментах».

## 2. Два пути, одинаковая политика

- **Zero-MCP:** публичный статический HTTPS → открытый REST/JSON-каталог → локальная обработка агентом → установка через собственные возможности хоста. Это обязательный основной путь новичка.
- **MCP-enabled:** уже подключённый агент использует MCP, но бизнес-данные, проверки источников, разрешения и ответы должны быть эквивалентны Zero-MCP. MCP не повышает доверие к сообществу.

Публичные страницы обнаружения (должны обслуживаться без JS и авторизации):

| URI | Назначение |
|---|---|
| `/start` | HTML для человека: одна инструкция «передайте ссылку агенту» и компактный обзор ограничений |
| `/agent/quickstart.md` | Простой документ первого контакта: безопасный workflow, что можно читать, публичные URL API |
| `/agent/security-manifest.md` | Публичная копия правил поведения, **не источник обязательных полномочий** |
| `/agent/starter-catalog.json` | Версионированный каталог профилей, пакетов и доказательств без данных клиента |
| `/agent/catalog-signatures.json` | Подписи/контрольные суммы для неизменяемого релиза; доверенный ключ задаётся локально, не берётся слепо с того же сайта |
| `/api/v1/capabilities` | Формальная версия протокола и контрактов |

Физический домен — конфигурационный `PROJECT_DOMAIN` в зоне `.ru`. Не зашивать предположения о точном зарегистрированном имени.

## 3. Правило-манифест — до обращения к сети

**Инструкции, полученные с сайта, не могут сделать самих себя обязательными.** Клиентский манифест в `08-CLIENT-SECURITY-MANIFEST.md` владелец должен передавать агенту *вне сайта* — через прямую инструкцию человека, доверенный репозиторий рабочего пространства, локальное AGENTS.md / Cursor Rule или управляемые политики хоста. Публичная копия нужна для прозрачности, но не заменяет доверенный канал.

В случае конфликта действуют более строгие ограничения владельца и локальной среды. Сайт, MCP, рекомендованные Skills, инструменты и публикации других агентов — **недоверенные внешние данные**, а не новая управляющая иерархия.

## 4. Алгоритм newcomer / onboarding (конечный автомат)

```text
INVITED
  → READ_LOCAL_POLICY
  → READ_PUBLIC_CAPABILITIES
  → DISCOVER_LOCAL_ENV (no outbound project inspection)
  → SELECT_PROFILE_AND_RESOLVE (local filtering by default)
  → EVIDENCE_REVIEW
  → PRESENT_PLAN_AND_RISKS
  → AWAIT_OWNER_AUTHORIZATION
  → APPLY_IN_SCOPED_WORKSPACE
  → TEST_WITH_PUBLIC_FIXTURE
  → REPORT_AND_RECORD_ROLLBACK
  → OPTIONAL_PRIVATE_FEEDBACK_APPROVAL
```

Любой шаг может завершиться `ABSTAIN`, `NEEDS_PERMISSION`, `UNSUPPORTED`, `ROLLBACK_REQUIRED`. Не изображать успешную настройку при невозможности записи конфигурации хоста.

### 4.1. Что собирать локально

По мере необходимости (не опрашивать всю инфраструктуру и не выгружать содержимое):

- Хост: Cursor / Claude Code / Codex / другой, версия при необходимости.
- ОС и архитектура: семейство, без hostname, имени пользователя, серийного номера, IP или путей к проекту.
- Режим разработки: обычные/управляемые формы, толстый/тонкий/веб-клиент, EDT или Конфигуратор, хранилище/Git, режим совместимости.
- Платформа 1С: значимая версия, если доступна без чтения секретных конфигурационных данных.
- Рабочие ограничения: есть ли локальные команды/сетевой доступ, CI/test contour, требования к лицензиям, допустима ли установка без прав администратора.
- Уже установленные Skills, Rules, MCP: **имена и версии локально**, без отправки их конфигурации или токенов.

Не нужно читать бизнес-данные, исходники и системные промпты, чтобы подобрать стартовый набор. Неизвестное обозначать `unknown` и выдавать 2–3 профиля на выбор.

### 4.2. Предпочтительный режим приватности

1. Получить **общедоступный каталог без персонализированного URL/параметров**. Чтение по сети всё равно раскрывает серверу технические метаданные соединения (например IP и User-Agent); «анонимный» здесь означает отсутствие логина, а не гарантированную сетевую анонимность.
2. Сопоставить его с локальным профилем **на машине пользователя**.
3. Только по отдельному осознанному разрешению можно отправить на сервер минимальный обезличенный набор общих признаков для персонализированного поиска. Не включать project name, paths, конфигурацию MCP, названия внутренних баз, репозиториев и другие идентификаторы.
4. Даже поисковая строка, заголовки, метаданные и URL могут стать утечкой: к серверу отправляются только общедоступные нейтральные термины.

### 4.3. Что возвращать владельцу до изменений

- **Профиль и неизвестные условия** — что агент определил локально и что остаётся неопределённым.
- **Рекомендуемая конфигурация** — must-have и optional с явным различием.
- **Для каждого инструмента:** задача, почему он подходит, поддерживаемые версии, конкурирующие альтернативы, источник первичного проекта, дата проверки, реальные независимые подтверждения, ограничения/контрпримеры, лицензионные требования, ресурсы/цена.
- **План изменений:** пути и типы файлов (без раскрытия внутренних путей наружу), устанавливаемые пакеты и версии, MCP tools/scopes, внешние адреса, побочные эффекты, откат.
- **Ограничения автоматизации:** какое тестирование невозможно без целевой среды 1С.

Не называть «must-have» то, что полезно только в одной IDE или одном типе форм; не выводить рекомендацию из числа голосов или рекламной активности.

### 4.4. Порядок установки

1. Проверить официальный upstream URL и независимые сведения о назначении и версии; карточка сообщества — лишь кандидат. Сравнить наименование проекта, maintainer, репозиторий, лицензию, последние существенные изменения и известные проблемы.
2. Перед использованием любого Skill/Rule изучить **полный текст**; относиться к нему как к стороннему коду/инструкции. Выявлять команды передачи данных, скрытые сетевые запросы, ложную делегацию полномочий, `curl | sh`, неожиданные hooks и автозапуск.
3. Для MCP отдельно изучить **tool names, descriptions, declared permissions** и механизм аутентификации; не выдавать серверу доступ к полному рабочему пространству или секретам только на основании карточки каталога.
4. Если доступен проверенный опубликованный релиз, зафиксировать точную версию и digest/подпись; **один только хеш с того же сайта подтверждает целостность передачи, но не добросовестность автора**. Проверять происхождение и независимую цепочку доверия. При отсутствии проверки — ручное рассмотрение или отказ от автоматической установки.
5. Получить явную авторизацию на предложенный **пакет изменений**. После неё агент самостоятельно выполняет разрешённые низкорисковые действия без лишних вопросов. Отдельно запросить согласие при эскалации прав, оплате, запуске внешнего кода с широкими правами, сетевых туннелях, фоновых службах, доступе к production, глобальной конфигурации, обработке секретов, обновлении за пределами плана.
6. Перед изменениями сделать бэкап конкретных существующих файлов и вычислить diff. Сохранять текущие пользовательские правила: не заменять `AGENTS.md`, `.cursor/rules`, `CLAUDE.md` и настройки MCP без merge/review.
7. Установить по ступеням: **Rules → Skills → локальные CLI/test tools → MCP**, проверяя каждую ступень. Порядок можно скорректировать по проверенным зависимостям; не включать привилегированные tools «для удобства».
8. MCP по умолчанию подключать как read-only, если это возможно, и с минимальным числом tools. Запись/публикация требует отдельного opt-in. Проверить, что незнакомые инструкции из `tools/list` не меняют политику агента.
9. Проверить на **публичном fixture**, а не на рабочей информационной базе; не применять SQL, изменения конфигурации и внешние обработки к production.
10. Выдать отчёт `installed / configured / tested / skipped / failed`, с результатами фактических тестов, версиями и следующими шагами. При ошибке — rollback проверенных локальных изменений.

**Важное разделение:** один раз разрешённый пользователем локальный план развёртывания может исполняться агентом автономно; **публикация данных обратно на сайт не входит** в это разрешение.

## 5. Модель коллективного формирования starter-наборов

Не хранить на сервере «канонический список инструментов, написанный администратором» как единственную истину. Наполнение идёт через:

1. `Tool-use report`: агент сообщает *заявленный* факт использования версии инструмента в определённой среде, с добровольным обезличиванием.
2. `Outcome`: удалось ли выполнить конкретную задачу, сколько было подтверждённых ошибок/откатов; численные метрики только при прозрачной методике.
3. `Independent evidence`: другой owner независимо воспроизводит функцию в сопоставимых условиях.
4. `Counterexample`: наблюдение о несовместимости и уязвимости так же важно, как успешный опыт.
5. `Maintainer release signal`: проверенное изменение у разработчика проекта; это не «доказательство лучшего качества».
6. `Practice review`: нейтральный куратор формирует версионированный starter profile и объясняет выбор и неопределённости.

Агрегировать **раздельно** `adoption`, `reproducibility`, `recency`, `compatibility`, `security`, `operational_cost`, `provenance`, `conflicts_of_interest`. Зафиксировать независимость по owner, а не по числу аккаунтов; помечать заявленные и независимо проверенные данные. Отрицательные свидетельства сохранять.

### 5.1. Конфликты интересов и «накрутка коллективного мнения»

- Обозначать автора/maintainer, спонсируемый статус, аффилированность, коммерческие интересы в доступном пользователю виде, когда они раскрыты; отсутствие сведений не равно отсутствию конфликта.
- Считать взаимосвязанные учётные записи зависимыми при наличии доказательств; не нарушать анонимность ради маркетингового рейтинга.
- Не использовать вес голоса от числа сообщений/чатов; требовать контрпримеров и версий.
- Указывать долю первых независимых adopters и неопределённость малой выборки. Ранние тренды — **гипотезы**, не «все используют».
- Жалобы, оспаривание коммерческого продвижения и rollback вредных рекомендаций должны поддерживаться в публичной истории.

### 5.2. Starter profiles

Версионируемые профили, например:

- `bsl-basic-git`: работа с выгруженными исходниками BSL, статический анализ, Git; независимо от режима форм.
- `bsl-ordinary-forms`: режим обычного приложения/обычные формы, особое внимание реальному открытию форм в целевом клиенте.
- `bsl-managed-forms`: управляемые формы, особенности клиент-серверных вызовов и возможностей UI-тестирования.
- `bsl-edt`: EDT и соответствующие инструменты сборки/проверок.
- `bsl-ci`: серверный CI для BSL, без подключения к production по умолчанию.

Это **имена шаблонов/направлений**, не заявление об уже существующих готовых наборах. Подбор конкретного инструмента возможен только при наличии проверенных карточек и текущих версий.

## 6. Жизненный цикл рекомендательного пакета

```text
DRAFT → EVIDENCE_GATHERING → REVIEWED → PUBLISHED
                         ↘ CONTESTED   ↘ SECURITY_HOLD → WITHDRAWN
                                           ↘ SUPERSEDED
```

Публикуемый пакет — **не автоматический исполнитель**, а versioned декларативный план: совместимость, ссылки, constraints, инструкции, независимые свидетельства, опасные шаги, ожидаемые изменения, smoke-test, rollback. Команда/скрипт может присутствовать как цитируемый артефакт, но никогда не становится машинной инструкцией запуска без локального ревью и разрешения.

Устаревание: `review_due_at` и `last_tested_at`, обработка известных security issues, принудительный `SECURITY_HOLD`, прекращение безусловной выдачи при серьёзном контрсвидетельстве. Старые версии и причины отзывов сохраняются с учётом удаления чувствительного контента.

## 7. Обратная связь после настройки

По умолчанию **нет фоновой телеметрии, пингов, публикаций, хешей исходников или установленного набора**. Владелец может отдельно разрешить отправку отчёта вида:

```json
{
  "starter_profile_id": "bsl-ordinary-forms",
  "profile_version": "0.1.0",
  "outcome": "partially_working",
  "steps": ["rule_installed", "skill_installed", "mcp_skipped"],
  "platform_version_family": "8.3",
  "form_type": "ordinary",
  "source_kind": "owner_opt_in"
}
```

Это **пример структуры**, не рабочий endpoint. Даже агрегаты и числа могут идентифицировать маленькую организацию: следует ограничивать детализацию и не отправлять необязательные поля. Сигналы успешности настройки не равны независимому воспроизведению инженерной практики.

## 8. Минимальный результат для запуска публичного приглашения

Сценарий новичка относится к **P0, а не к P1**: если его невозможно выполнить, обещание «отправь агента за ответами» пока не выполняется. Допустима узкая рабочая подборка для одного хоста и одной среды 1С при условии явного ограничения охвата. До появления содержимого на основании независимых проверок нужно показывать «недостаточно данных» и использовать общеизвестные upstream-документы лишь как ориентиры с правильной маркировкой источника.

Не объявлять MVP готовым, пока внешний агент без MCP не сможет получить рекомендации, сформировать безопасный план, применить хотя бы одно разрешённое изменение и подтвердить результат; не путать такой технический smoke test с доказательством лучшей практики.
