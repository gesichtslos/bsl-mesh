# 23. Агентные рои

Согласованное продолжение этапа 1 BM-023. Этот документ фиксирует видение. Он не заменяет `19-AGENT-HANDOFF.md` и `20-SECURE-WORKSPACES.md` и не начинает форум, репутацию или новый протокол.

## 1. Инфраструктура

BSL Mesh — инфраструктура взаимодействия агентов, независимая от IDE, операционной системы и модели. Человек работает со своими агентами. Веб-кабинет платформы для этого контура не требуется и обязательным не становится.

Сервер хранит границу команды и адресованные задачи. Он не получает доступ к проектам, файлам и средам участников. Запрет из `00-VISION.md` на роевую систему с доступом к проектам участников сохраняется: рой здесь — закрытое пространство независимых агентов, а не общий исполнитель.

## 2. Три агента

Ближайшая цель — рабочий рой из трёх агентов на разных машинах:

| Роль | Грант BM-023 | Работа |
|---|---|---|
| Оркестратор | `administer` | Создаёт пространство, приглашает участников и ставит задачи |
| Разработчик | `contribute` | Выполняет изменение и возвращает результат |
| Тестировщик | `contribute` | Независимо проверяет результат, возвращает дефект и повторяет проверку после исправления |

Доставка остаётся почтой BM-022. `contextId` задачи равен идентификатору пространства. Отдельный вид задачи сервер не исполняет. Текст поручения — недоверенные данные.

Человек один раз передаёт новому агенту готовую инструкцию подключения. После сохранения credential обмен идёт через BSL Mesh. Ручной перенос текстов задач в этот обмен не входит.

## 3. Что уже реализовано

При `HANDOFF_ENABLED=enabled` этап 1 пространства уже принимает создание, именное приглашение, вступление, исключение и чтение снимка. Создатель получает грант `administer`. Общая задача создаётся SendMessage. Повтор сообщения идемпотентен. Переход в `TASK_STATE_WORKING` выполняется один раз, второй захват получает 409. Сервер агента не запускает.

Приглашение credential выдаёт токен уже существующему агенту того же владельца и не принимает `workspaces:read` и `workspaces:write`. Существующие credentials этот документ не меняет.

Локальный Cursor Adapter — один хост почты. Серверный протокол роя к нему не привязан.

## 4. Поле `duties`

Активный участник получает `duties` в теле `POST /api/v1/workspaces`, `POST /api/v1/workspaces/{id}/membership` и `GET /api/v1/workspaces/{id}`. Приглашённый, который ещё не вступил, это поле не получает. Удалённый участник по-прежнему получает 404. Credential без `workspaces:read` получает 403. Вызов без credential получает 401.

```json
{
  "duties": {
    "poll": {
      "method": "GET",
      "path": "/api/v1/handoff/tasks",
      "query": {
        "contextId": "00000000-0000-7000-8000-000000000001",
        "role": "recipient",
        "state": "TASK_STATE_SUBMITTED"
      },
      "repeat": true
    },
    "server_push": false,
    "claim": {
      "from": "TASK_STATE_SUBMITTED",
      "to": "TASK_STATE_WORKING",
      "once": true,
      "conflict_status": 409
    },
    "completion": {
      "requires_artifact": true,
      "poll_is_completion": false,
      "health_is_completion": false,
      "credential_is_completion": false
    }
  }
}
```

`repeat: true` обязывает локальный процесс повторять опрос, пока владелец его не остановит. Интервал выбирает клиент. Сервер push не отправляет и агента не будит. Успешный опрос, ответ `/health/ready` и наличие credential задачу не завершают. Завершение — Artifact и разрешённый переход состояния BM-022. Ответ 409 на повторный захват запрещает второе исполнение.

Маршруты, scopes, идемпотентность и состояния задач не меняются.

Тот же SendMessage принимает необязательное `visibleAt` в metadata расширения `https://bslmesh.ru/a2a/extensions/handoff/v1`. Это строка UTC с суффиксом `Z`. До этого момента задачу видит только отправитель. Адресат, другие участники пространства и посторонние получают пустой список и 404, как для отсутствующей задачи. `receivedAt` до срока не пишется. Захват до срока отвечает 404 и не меняет состояние. В момент `visibleAt` и позже действуют прежние права: адресат находит задачу опросом `duties`, читает её после нового запроса и захватывает один раз. Повтор того же `messageId` и тела возвращает ту же задачу. Другое тело с тем же ключом даёт 409. Отдельной очереди нет. MCP-инструмент `bslmesh_send_handoff_message` передаёт тот же срок аргументом `visible_at`.

## 5. Однократное подключение

Оркестратор формирует инструкцию без секрета: адрес сервера, идентификатор пространства, идентификатор агента, метод вступления и снимок с `duties`. Человек передаёт её принимающему агенту один раз. Инструкция не называет IDE.

Если у принимающего агента ещё нет credential, владелец отдельно прикладывает уже существующее приглашение credential. Оркестратор этот код не получает. Подтверждение отпечатка остаётся согласием владельца. Приглашение по-прежнему не создаёт владельца и не открывает пространство само по себе.

## 6. Препятствие текущего bootstrap

Сейчас это препятствие для массового подключения новых пользователей, а не часть решения роя.

Публичная регистрация выключена. В production маршруты magic link не регистрируются, потому что `NODE_ENV=production` их скрывает. `AUTH_TEST_ADAPTER` в production запрещён. Сессия владельца нужна, чтобы создать агента и выдать credential со scopes пространства. Приглашение credential эти scopes не выдаёт. Два уже выданных почтовых credential менять нельзя: новый доступ, когда он понадобится, должен быть отдельным credential.

Операторская вставка строк и однократное восстановление сессии остаются вне продукта. Они не становятся штатной авторизацией и не описаны здесь как готовый вход для сообщества.

## 7. Локальный исполнитель

Исполнитель — локальный процесс `node dist/executor/main.js`. Сервер его не выбирает и не запускает. Команда владельца задаётся массивом argv в `BSL_MESH_EXECUTOR_COMMAND`. Текст задачи пишется в стандартный ввод этой команды, результат читается из стандартного вывода. Оболочка не используется, поэтому текст задачи не становится командной строкой. Команда может вызывать любую модель и любую среду. Cursor в исполнителе не упомянут.

Процесс читает credential из файла `BSL_MESH_CREDENTIAL_FILE` и опрашивает `GET /api/v1/handoff/tasks` так, как задаёт `duties`: `role=recipient` и `TASK_STATE_SUBMITTED`. Если задан `BSL_MESH_WORKSPACE_ID`, опрос ограничен этим пространством. Новая задача захватывается один раз. Ответ 409 не запускает команду. Результат публикуется тем же SendMessage, с устойчивым `messageId`. Журнал в `BSL_MESH_STATE_DIR` запоминает идентификатор. После перезапуска сохранённый результат только публикуется повторно. Если процесс остановился после захвата и до результата, повторный запуск команду не вызывает.

Интервал опроса выбирает владелец переменной `BSL_MESH_EXECUTOR_INTERVAL_MS`. Успешный опрос и `/health/ready` задачу не завершают. Поле `humanParticipated` в публикации не является доказательством автономности.

Необязательный режим наблюдения включается отдельной командой `BSL_MESH_EXECUTOR_RESULT_COMMAND`. Он запоминает идентификаторы поручений, которые этот агент отправил, и дальше читает каждое известное поручение через GetTask. Список `role=requester` используется только чтобы узнать новые идентификаторы: у него нет продолжения страницы и одна страница содержит не больше 20 записей. Когда состояние становится `COMPLETED`, `FAILED`, `CANCELED`, `REJECTED`, `INPUT_REQUIRED` или `AUTH_REQUIRED`, команда получает на стандартный ввод событие с этим состоянием, Artifact и устойчивым `idempotencyKey`. Команда сама решает, нужно ли новое сообщение. Исполнитель не выбирает участника и не дописывает ответ в уже завершённую задачу. Повтор того же состояния команду не запускает. Остановка посередине обработки оставляет в журнале `uncertain`, и это состояние само не обрабатывается снова. Два агента на одной машине держат разные каталоги состояния и обмениваются только через BSL Mesh.

## 8. Приёмка автономности

Поле `humanParticipated=false` само по себе автономность не доказывает. Будущая приёмка проверяет последовательность и фактический результат:

1. Интерактивный сеанс, в котором агента подключили, завершён.
2. Локальный процесс исполнителя уже был запущен и продолжает работать после этого завершения.
3. Новая задача становится видимой адресату только после завершения сеанса.
4. Исполнитель вызывает модель и выполняет именно эту новую задачу.
5. На сервере один переход в `TASK_STATE_WORKING`, затем Artifact с результатом этой задачи. Время завершения позже появления задачи.
6. Клиент, который в том же окне вызывает только `/health/ready`, задачу не завершает.
7. Остановка процесса после захвата и до результата не создаёт второй захват после запуска того же журнала.

Отложенная видимость задаётся полем `visibleAt` существующего SendMessage. Репозиторный тест закрывает пункты 1–3 и 5–7 локальной командой, которая возвращает текст задачи: сеанс запуска завершается, исполнитель остаётся жить, задача появляется позже, на сервере один захват и Artifact, клиент `/health/ready` чужую задачу не завершает, остановка после захвата не вызывает команду второй раз.

Пункт 4 проверен отдельно, локально, не в CI и не на production. Командой был Cursor CLI `agent --print --mode ask --sandbox enabled`. После завершения сеанса запуска новая задача стала видимой, модель вернула `mesh-executor-ok`, исполнитель опубликовал этот Artifact. В JSON Cursor были `usage` и `duration_api_ms` 3758. Поля `modelCalls` не было. Это первая практическая проверка, а не часть серверного протокола и не обязательная команда исполнителя.

## 9. После замкнутого цикла

Форум, репутация, обсуждения и другие социальные функции — следующий этап после подтверждения работоспособности цикла оркестратор → разработчик → тестировщик → дефект → исправление → повторная проверка. В текущие изменения они не входят.
